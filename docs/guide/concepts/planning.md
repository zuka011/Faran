# Trajectory Planning

Motion planning, trajectory planning, trajectory optimization, path planning, and optimal control are a lot of different terms for describing similar, but subtly different, problems. Why call Faran a trajectory planning library specifically? 

- **Motion planning** is a broad term that can refer to any method for generating motion for a system. This includes approaches that are not optimization-based, such as graph search algorithms (e.g. A*), sampling-based planners (e.g. RRT), and others. At the moment Faran only supports optimization-based planners, and even there it only supports variants of a specific algorithm (MPPI). Calling Faran a motion planning library would be an overstatement for now.
- **Path planning** typically refers to the problem of finding a geometric path from a start to a goal state, often without considering dynamics or time. This is also the first problem solved in a hierarchical motion planning pipeline, followed by trajectory planning and then trajectory tracking (low-level control). As mentioned in the previous point, since Faran does not currently support path planning algorithms, this term would also not be accurate.
- **Optimal control** and **trajectory optimization** are similar terms that describe the same underlying problem with a slightly different emphasis. Both assume there is a system that evolves according to some dynamics, there exists an objective function to optimize, and possibly some constraints. The difference is that optimal control is looking for a control sequence that optimizes the objective, whereas trajectory optimization is looking for the desired sequence of states. Nevertheless, this is a lower level of abstraction than what Faran provides, and there are already libraries that handle it (e.g. <a href="https://github.com/casadi/casadi" target="_blank">CasADi</a>).

Although **optimal control** and **trajectory optimization** technically describe the problem Faran solves, this misses the point that Faran is not domain-agnostic bare-bones math. Faran does not provide many general-purpose optimization algorithms, but instead focuses on providing all necessary components to solve a real life **trajectory planning** problem (e.g. navigation for a mobile robot, automated driving) from start to finish. This includes components that are not related to optimization itself, such as motion prediction or state estimation. So, in the end, the term *trajectory planning* carries a more accurate connotation of what Faran can be used for without over-promising the scope the way motion planning would. Anyways, if you're already using this library, it doesn't really matter what you call it.
